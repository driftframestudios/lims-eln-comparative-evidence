# Deterministic comparison report projection

## Contract

- **What:** A repository-native route from admitted comparison inputs to
  deterministic runtime reports and one complete source-bound Pages candidate.
- **When:** Comparison output, report rendering or styling, projection source,
  manifest identity, or hosted report bytes change.
- **Boundaries:** The report retains its input evidence mode and authority.
  Publication supports inspection and grants no production authorization.
  Canonical origin, CNAME selection, release acceptance, and hosted promotion
  remain receiving decisions. Signed releases and accepted report identities
  remain immutable.
- **Result:** Machine-readable and human-readable report twins reproduce
  deterministically, projected runtime bytes equal their source outputs, and
  every public file is bound to one full source revision and SHA-256 identity.

## Rules

### Rule: Resolve the report family first

Name whether the work concerns Golden simulated verification, the planned
contract-shape exercise, or caller-supplied observed evidence. Preserve its
source, admission, and authority posture through every derivative.

### Rule: Derive from accepted coordinates

Use the released profile, admitted observations, and exact accepted producer
coordinates. Keep the Comparator release coordinate as the receiving identity;
it does not replace producer source identity.

### Rule: JSON and HTML are semantic twins

Treat `comparison.json` as the machine-readable report and
`comparison.html` as its exact human-readable rendering. Regenerate HTML from
the report and require semantic agreement rather than maintaining parallel
facts by hand.

### Rule: Runtime output fails closed

Require strict UTF-8 JSON, one complete two-file inventory, valid report
digest, regular-file boundaries, and two isolated byte-identical runs. Reject
duplicate keys, unexpected encodings, links, missing artifacts, and extras.

### Rule: Pages preserves runtime bytes

Build from one clean exact full revision. Copy runtime report files byte for
byte; create surrounding discovery, style, data-use, and manifest files
deterministically from committed source.

### Rule: Projection identity is complete

Bind every projected path to byte count, SHA-256, byte relation, and full
`sourceRevision`. Re-observe the source immediately before accepting the fresh
candidate destination.

### Rule: Presentation changes preserve semantic facts

A report-style correction may change HTML and projection byte identities while
the JSON facts and report digest remain stable. Use a focused narrow and
desktop observation when visible table behavior changes.

### Rule: Evidence posture survives publication

Preserve simulated, planned, and observed distinctions and the declared
assurance stage. A published report supports evaluation while its
`production_authorization_effect` remains `none` unless a separate authority
changes that contract.

### Rule: Promotion stays with its receiver

Keep canonical origin, CNAME, accepted source carrier, docs revision, release
acceptance, and hosted verification with their named receiver. The builder
produces a candidate; it does not select or promote the public deployment.

## Operating sequence

1. Name the report family, intended reader, changed behavior, and authority.
2. Resolve the exact profile, input, producer, Comparator release, and source
   coordinates.
3. Generate JSON and HTML twice in isolated destinations; compare complete
   inventories and bytes.
4. Validate report digest, semantic-twin rendering, evidence posture, and
   regular-file boundary.
5. Build two fresh Pages candidates from one clean full source revision.
6. Confirm exact runtime-byte reuse and compare complete projection inventories.
7. For visible changes, observe the changed behavior at one narrow and one
   desktop viewport.
8. Return source revision, report facts preserved or changed, exact validation,
   coverage boundary, and receiving publication decision.

## Completion

The route completes when both report twins and both Pages candidates reproduce
byte for byte; the manifest binds every projected file to one full source
revision; report authority and authorization posture remain explicit; and the
named receiver can accept, defer, or promote the candidate without inferring
missing coordinates.
