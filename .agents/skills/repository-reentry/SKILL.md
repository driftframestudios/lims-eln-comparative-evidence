# Comparative Evidence repository re-entry

## Contract

- **What:** A repository-local method for recovering settled, current, open,
  and next comparison state.
- **When:** Work resumes after a handoff, branch or pull request changes, or
  source, release, living orientation, and public projection appear to
  disagree.
- **Boundaries:** Runnable source and tests define current behavior. Signed
  release evidence defines the accepted comparison baseline. A public carrier
  records one published observation without turning delivery into semantic
  authority. Repository edits and receiving decisions stay with their named
  owners.
- **Result:** One authoritative source path, one live collaboration surface,
  the material difference among records, and one bounded next move.

## Rules

### Rule: Current source and accepted release answer different questions

Read the working branch for current behavior. Read the signed tag, release
receipt, and retained report identities for what was accepted. Read the docs
manifest and hosted observation for what was published.

### Rule: The nearest carriers come before broad history

Read the root README, release role, Machine Node, First Receipt, Coordination
Horizon, and constellation lock before searching the complete history. Follow
the exact Issue or pull request only when live coordination affects the move.

### Rule: Report families keep their evidence posture

Distinguish Golden simulated verification, planned contract-shape exercise,
and caller-supplied observed evidence. Re-entry preserves their source,
admission, and authorization boundaries.

### Rule: Source and projection identities remain separate

Record the accepted source revision, docs revision, manifest identity,
canonical origin, and report-byte relation independently. A later presentation
change may alter HTML and projection identities while semantic report facts
remain stable.

### Rule: Existing work remains intact

Identify unrelated worktree changes and neighboring worktree branches before
editing. Surface overlap instead of absorbing another collaboration's work.

### Rule: Stale status language becomes visible

When a living carrier describes a completed route as waiting, name the
difference and reconcile the living carrier through its validator. Historical
Issues and immutable release evidence retain their original record.

## Operating sequence

1. Run `git status --short --branch`; inspect local, remote, and tag history.
2. Read `README.md`, `release/repository-role.json`, `machine-node.json`,
   `first-receipt.json`, `COORDINATION-HORIZON.json`, and
   `constellation.lock.json`.
3. Identify the relevant profile, fixtures, runnable source, reports, and tests.
4. Resolve the signed release subject and any later main or docs carriers.
5. Inspect the live Issue, pull request, and hosted check only where current
   status or authority changes the route.
6. State settled, current, open, and next terrain; identify any stale carrier.
7. Choose one source path, one receiver, and one stopping event.

## Completion

Re-entry completes when a collaborator can name current comparison behavior,
the accepted release, the public observation when one exists, the material
difference among them, and the next bounded move without reconstructing the
entire repository history.
